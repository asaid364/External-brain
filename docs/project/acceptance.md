# 项目验收标准

原两页 UI 验证文档迁移至此。历史原型桌面浏览器验证见 [原型说明](../../apps/ui-prototype/README.md)。当前安卓记录代码及本地验证已交付，完整功能验收状态见 [验证证据](records/verification.md)，整个正式首版尚未完成；本文汇总验收口径，不声明通过，不将原型规则直接升级为正式产品决定。

## 适用范围

本文只定义验收行为和证据。产品目标见 [项目目标](goals.md)，阶段范围见 [边界](scope.md)，不可违反的约束见 [禁止项](prohibitions.md)，放行条件见 [门禁](gates.md)。浏览器验证不能代替真实安卓输入法、系统返回和后台调度验证。

## 正式安卓记录阶段

专门用例维护于 [记录验收](records/acceptance.md)，逐项结果须有对应证据，不使用历史浏览器结果冒充通过。用户已报告基本功能手动检查，但未提供逐项结果；不据此将 R01—R21 全部标为通过。记录阶段不含日报/同步业务，通过不等于整个首版放行。行为、时间、删除规则分别维护于 `records/`。

## Mobile MCP 安卓端到端测试工作方式

- 验证安卓界面和用户操作流程时，主 Agent 或测试 Agent 优先使用 Mobile Next Mobile MCP 操作安卓模拟器。先列出设备，再明确选定模拟器；每次调用携带该设备 ID，不依赖默认设备，不擅自操作真实手机。
- 每轮先明确当前版本（含已安装 APK 与源码对应关系是否确认）、设备与系统版本、授权范围、操作步骤和预期结果。参考适用的 R01—R21，不因接入工具自动扩大为完整测试。
- 优先读取当前界面元素定位，必要时结合截图坐标。操作后重新读取元素或截图确认状态，不盲目连续点击；元素引用与坐标不跨页面沿用。
- 使用合成测试数据和可识别的测试标记，先识别已有记录，避免修改或删除非本轮测试数据。记录本轮新增及遗留数据；清理也须在授权范围内。
- MCP 用于端到端操作验证，不替代必要的编译、单元测试与底层数据验证。以预期业务结果及数据状态判断，不把“成功点击”“没有崩溃”当作功能通过。
- 每项结果标记为通过、失败、阻塞或无法确认，并附实际操作和证据。没有实际执行的功能明确写“未验证”；用户手动检查不代表未测试功能或后续修改通过。
- 失败时保留截图、必要日志、复现步骤和测试后遗留数据说明；证据先放本机被忽略的 `apps/android/app/build/mobile-mcp/`，可能含已有记录，不将原始截图、界面树或日志直接提交仓库。文档只记录脱敏结论，必要证据按授权另存，构建清理可能删除该目录。
- 安装或升级 APK 必须在当前任务授权内并保留现有数据；不得擅自卸载、清除数据、重置模拟器或降低版本。工具名称不保证安装参数安全，执行前核实实际行为。签名、版本或兼容性冲突时报告阻塞，不以删数据绕过。
- MCP 暂时不可用时报告实际错误及限制；必要的只读 ADB 诊断可补充设备、版本等信息，但不得冒充 MCP 连接或端到端测试结果。
- 由主 Agent 或测试 Agent 执行测试；Designer 负责 UI 和交互设计，视觉/交互调整携带证据协调，不改变现有角色模型配置。
- 测试规则不自动授权修改系统设置、使用云端设备、清除数据或扩大测试范围。连接验证仅检查工具加载、模拟器枚举、截图/元素、应用启动与页面识别，不进行业务写入。


## 交付

- 可操作原型，代码放在 `apps/ui-prototype/`，同时给出准确运行和手机访问方法。
- 两页的布局、公共组件、文字样式与主要交互说明。
- 空数据、长文本、键盘弹起、加载、离线、失败重试、保存反馈状态。
- 模拟数据清单与尚未实现的能力说明。
- 设计与开发协作时，公共组件、导航指定单一负责人；修改约定范围之外文件前与主 Agent 协调。

## 手机验证任务

| 页面 | 任务 | 观察 |
|---|---|---|
| 记录 | 输入“刚看完一小时教程，还没实践”，保存 | 是否容易找到入口、理解已保存状态 |
| 记录 | 补记昨天、修改已有内容 | 是否明确发生时间与录入时间 |
| 记录 | 长文本，模拟离线与失败 | 按钮不被遮挡，内容不丢失，重试不重复 |
| 日报 | 阅读事实草稿 | 活动顺序和缺失信息是否易理解 |
| 日报 | 回答 1—3 个补充问题中的适用项，或跳过，再更新草稿 | 补充是否可追溯、更新是否清楚；原型当前展示一个问题 |
| 日报 | 查看关联原始记录并纠错 | 是否易核对、易返回 |

## 初始验收建议

- 打开到保存一句短记录通常在约 15 秒内；作为试用参考，不是已确认的性能承诺。
- 能分辨本地保存成功、等待同步、保存失败。
- 切换页面或失败时，已输入文字保留。
- 能发现并修正日报中的一处错误或遗漏。
- 试用时记录“想做什么—卡在哪里—期望行为”，优先修复最影响记录的三个问题。

本次按用户完整原型任务验收范围实现并进行浏览器验证。不能把模拟状态的通过当作真实 AI 或同步已通过验证；正式原生应用的数据持久化方案仍需单独实现和验证。

## 原型完整验收清单

1. 新增、补记、修改后刷新内容保留，发生时间、录入时间与修改历史可区分。
2. 未保存记录草稿切页、刷新后仍存在。
3. 保存失败保留文字，重试不重复创建；真实 localStorage 写入失败不能显示成功。
4. 日报按所选日期的记录生成，补充保存为独立记录后可以更新；没有记录不编造活动。
5. 日报可查看来源并进入纠错；更新不能静默覆盖手动修改，应明确确认或保留版本。
6. 演示入口覆盖空、生成中、AI 失败与重试、离线、保存失败、等待同步；退出不删除记录。
7. 区分本机保存与尚未同步；AI、网络、同步模拟明确标记，不展示虚假成功。
8. 重置有确认步骤和清除范围；提示清除浏览器数据可能丢失内容。
9. 360—430px 长中文无横向溢出，输入与按钮可用；真实安卓另外验证输入法、触摸、返回。
10. 构建与类型检查通过；代码、锁文件、环境、命令、手机访问及限制说明齐全。
11. 历史原型按发生时间的本地日期归属且不拆分跨午夜文本；正式安卓时间规则已确认，见 [时间与时区](records/time.md)，不以旧原型行为代替验证。

## 正式首版验收口径

以下依据已确认需求和任务清单整理；具体协议、凭据保存、定时与版本策略须先确认，再细化用例，不凭原型验证放行。

| 领域 | 验收要求 | 必要证据 |
|---|---|---|
| 安卓记录 | 文字记录、补记、纠错与历史；发生/录入时间分开；离线本地保存及重启读取正确 | 真实安卓操作与保存结果 |
| AI 日报 | 用户配置服务与模型；真实生成只整理事实；重要补充可跳过且可追溯；手动修改受保护 | 真实请求结果、来源核对及失败场景，日志不泄密 |
| 定时日报 | 按确认时间生成，按确认规则处理后台限制和错过执行 | 实机调度及补执行结果 |
| Windows 同步 | 同一可互通局域网自动同步原始记录和日报；电脑离线等待；恢复后按确认规则处理重传、冲突、删除 | 真实安卓/Windows 传输、中断恢复和两端内容核对 |

## 阶段分析与后续范围验收

- 阶段分析：用户设期限、确认关注能力；到期分析能力与成果及重复问题，结论可追溯记录；证据不足保持未知，延长观察由用户决定。
- 行动计划：讨论后由用户确认，不把 AI 建议当作承诺；不以时长直接判断成长。
- 核心价值：记录是否帮助发现此前未注意到的重复问题并改变行动；没有证据不得预填成功。
- 云端、其他用户与语音仍待开发，具体实现方案确认后补充可执行验收用例，不作为当前原型门槛。
